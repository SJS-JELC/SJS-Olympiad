# Application API contract

This contract describes the current implementation boundary. Server state and marking are authoritative. Browser presentation files contain no answer keys.

## HTTP and sessions

All endpoints use `/api/olympiad/{action}`. GET: `availability`, `session`, `events`, `teams`, `schools`, `leaderboard`, `diagnostics`. POST: `login`, `logout`, `event-create`, `event-setup`, `event-update`, `event-year-change`, `event-activate`, `event-draft`, `event-end`, `school-create`, `school-delete`, `school-colours`, `school-rename`, `school-teams`, `school-link`, `school-resume`, `codes-update`, `team-add`, `team-release`, `team-delete`, `claim`, `start`, `breach`, `recovery`, `resume`, `hydrate`, `question`, `draft`, `submit`, `action`, `practical`, `practical-save`, `question-content`, `practical-content`, `content-asset`, `content-catalogue`.

Opaque HttpOnly role cookie; server derives role/team/event/year. Teachers select an event with `eventId` on question/preview requests; competitors cannot override their bound event. Teacher sessions last eight hours. Codes initially 1234 competitor and 5678 teacher, hashed server-side; changes preserve issued sessions. Login returns a session snapshot. Logout never releases a claim.

Teacher catalogue previews use `eventId: catalogue-L5|catalogue-U5|catalogue-L6|catalogue-U6`. These validated year contexts do not create/edit events, bypass event timing and remain isolated and unscored. Competitors cannot use them to override their bound event or year.

Session snapshot: `{ role, expiresAt, serverNow, configRevision, activeEvent, events?, team, competition: {status, epoch}, score, attempts }`. `role` is `competitor` or `teacher`; absent authentication is 401. `activeEvent` is the active event, otherwise latest draft (legacy field name), null or `{id,name,year,endsAt,status,revision}`. Team is null or `{id,name,eventId,year,claimGeneration}`. Competition uses NOT_STARTED/ACTIVE/LOCKED. Teacher previews have no team or competition score writes.

Events are draft/active/ended (displayed as Draft/Active/Complete), one unfinished event maximum (draft and active combined); creation is guarded by the conditional settings write. Drafts as well as active events may be completed with confirmation. Active year is immutable; ended events never restart. Schedules use UTC epoch milliseconds: `theoryStartsAt`, `theoryEndsAt`, `practicalStartsAt`, `practicalEndsAt`. New events require the theory pair; practical is an optional complete pair. Each start precedes its end; overlap between phases is permitted. `endsAt` is a derived compatibility output equal to the latest configured end. London wall-time forms reject nonexistent or ambiguous DST values. Legacy reads normalize theory start to null/unbounded, theory end to old endsAt and practical to null without rewriting stored events.

Ending/switching requires explicit teacher confirmation. Event edits/transitions carry `expectedRevision`; code changes carry `expectedConfigRevision`. Stale edits conflict rather than overwrite newer settings. `event-create` returns `createdEventId` so the client selects its own created event even during concurrent staff changes. Current event settings and server acceptance time define an in-flight operation snapshot; accepted work may finish against its original event. No cross-partition global transaction claim.

## Hydration and request policy

GO/start returns `hydration: {eventId,year,serverNow,eventEndsAt,score,questions}` with every registered question in the active year, including blank answer state, confirmed outcomes and revision only, with no custom interaction or data. Teacher POST `hydrate` accepts `{eventId?}` and returns the same shape once per event/catalogue context. Reads use one question-partition listing and create no question/tick receipts. Only the selected `question` read may project elapsed timed/GC deadlines; completed state remains frozen. Private marking state and future timed prompts are never serialized.

First opening of every registered question/practical loads protected presentation/assets; subsequent valid-context visits use memory. Selected timed/GC state uses one authorized `question` read. Ordinary edits and internal navigation make no state requests. CHECK sends one direct `submit`; retries retain its frozen ID/payload. Timed start/name checks/deadline and GC Run/completion retain necessary server actions. Practical autosave remains separate. No operation adds a session preflight, and there is no recurring session poll.

## Questions

`question` takes `{questionId,eventId?}` and returns `{attempt, revision, score, serverNow, eventEndsAt, data?}`; its compatibility `eventEndsAt` is the theory end. Competitor reads/submits/actions require the theory window in both draft and active events. Claims/fullscreen entry/recovery use overall event availability, so competitors may enter before theory and wait in a countdown; closing theory hides content without creating a breach or resetting state. Teacher previews bypass theory timing. Practical uses a separate window and persistence contract below. Attempts retain the existing answers/feedback/retryAt/solvedAt/interaction presentation shape. Feedback is whole-question only. Additional public datasets (for example GC traces) use `data`; future timed answers never appear there.

`draft` is retired and returns 410 after access checks. The current frontend never calls it. Theory working stays only in mounted page memory: answers/drawings (including successful submissions), undo, group selections, GC formulation and reports. `submit` takes `{questionId,eventId?,requestId,answers}`; the marker evaluates that transient payload and persists only outcome/cooldown/completion metadata. Raw working is absent from new question rows and receipt snapshots for both competitors and teacher previews. Existing historical content is filtered on question/session/hydration reads and receipt replay, without a cleanup/migration or changing stored completed rows.

`action` takes `{questionId,eventId?,requestId,action}`. Only L6P3 `start`/`tick` and U5P5 `gc-run`/`tick` remain server operations. Retired grouping/GC presentation actions return 410. GC Run requires captured `{sample,concentration}`; the server chooses ID and a 4000ms deadline. Only the current run capture and next ID remain in the question record. A completion response/receipt carries `gcCompletedRunId`, not a report/measurement snapshot. The page builds its local report from its captured active run; fresh hydration has no report history. Run receipt snapshots keep ID/timing without the captured sample/concentration; the matching frozen request supplies those on retry. L6P3 retains the active sequence as private CSV row IDs plus prompt/progress/deadline, never the typed wrong name; inactive sequences are discarded on the next authorized write.

Responses retain the existing attempt shape but `answers` is empty. The page merges server outcome/timing into local working, clearing timed input when its prompt advances. Fresh entry starts with blank working; completed restored questions display their result/stamp without restoring their old answer. Request IDs bind operation/question/canonical payload through compact fingerprints and canonical outcome receipts. Same ID with different content is 409. Keep those receipts to prevent duplicate awards/restarted cooldowns; never recompute a replayed outcome from later state. Payload/HTTP size limits and ownership/security fences remain. Client clocks, score, correctness and year never authorize a mutation. Practical records and autosave are unchanged.

Backend marker module `api/src/questions.mjs` exports `questionInfo(id)` and `reduceQuestion(id, previous, action, now)`. Info is `{id,year,points,cooldownMs}`. Previous is `{state,privateState}`. Result is `{state,privateState,award}`; `award` is true only for the first unsolved-to-solved transition. Actions include `{type:'submit',answers}` and existing custom interaction actions, with all `now` fields ignored in favour of server time. Answer validation is separate from marking; retired draft requests cannot persist working. Custom module `api/src/custom-questions.mjs` exports `customInfo(id)` and `reduceCustomQuestion(id,previous,action,now)` (null for unsupported IDs). Private state is stored beside the public question state but never returned. Standard submissions do not return per-part feedback.

Team summary, question state and idempotency receipt share a per-team partition. Mutations conditionally fence the team claim/security generation and question revision. Release revokes ownership while retaining results and deadlines. Preview state is isolated from team partitions and never updates ranking.

Once solvedAt is confirmed, question state, private state and revision are immutable for subsequent accepted actions/ticks/submissions. Canonical receipts still bind new request IDs and reject reuse with different content; scores and ranking time cannot change again. The frontend freezes all question interactions without hiding readable scientific content or disabling header navigation.

`team-delete` is teacher-only and takes `{eventId,teamId,teamName,requestId,confirm:true}`. Completed events reject new deletions. Draft or active teams without submitted activity are permanently deleted; submitted teams in either status become retained excluded tombstones with reserved names. Activity includes zero-score wrong attempts and timed/server interactions, recorded atomically with submissions; older records are inspected compatibly. Both branches first revoke ownership/security generations and exclude the team from selection and ranking. Bootstrap/import/auth repair, team creation and deletion share one per-team lifecycle fence in their conditional transactions; an absent fence is guarded by transactional creation. Permanent cleanup retains that fence/admin receipts and uses conditional transaction chunks, preventing migration resurrection, stale generation reuse and stale cleanup deleting a recreated team. Reusing the same request is safe; the response includes `outcome: deleted|removed` and current teams. Development validation uses isolated memory data.

GC Enter, Load, dilution and report controls are local. Run sends one action with the captured sample/concentration; the server validates 0-100 in half-percent steps, keeps Mystery undiluted and starts the authoritative run. One completion action reconciles its deadline. Run IDs, deadlines, completed result snapshots and marking remain server-owned.

U5P9 retains the `drawings` field for both legacy carbon-only slot data and the shared editor's single molecule state. Local bounded undo history is stripped before transport/persistence. Legacy reads preserve atom IDs/connectivity through unique remapping, do not silently overwrite saved state, and retain oversized drafts intact in a read-only fallback. New submissions validate three distinct components against the unchanged private graphs after valid explicit/implicit hydrogen normalization. Question-specific editor bounds do not relax P3's existing defaults.

## Practical responses

`practical` takes `{eventId?}` and returns `{year,revision,responses,finalField,serverNow,eventEndsAt,readOnly,updatedAt}`. Each response is null or `{text,value}`: the exact entered numeric text and its finite parsed number. `practical-save` takes `{eventId?,requestId,expectedRevision,changes}`, where changes maps original response IDs to numeric strings or explicit null clears. Only the event year's fields are accepted: L5 and U6 use `numPracticalResponse1..4`; L6 uses only `numPracticalResponse3..4`. The final field is response4; a nonempty intermediate field does not constitute a final answer, and zero is not blank.

Competitor reads and writes require authenticated, ACTIVE Competition Mode with current ownership/security generations. The independent practical window authorizes writes; after its end, reads expose acknowledged responses read-only even after overall scheduled closure, while the session/claim/security binding remains valid. Teacher practical screens use local-only inputs outside timing, with no save requests, save-status messages or navigation flush. Competitor saves and server authorization remain unchanged. Teacher `teams` results include practical working/final values for the selected event, including completed events.

Updates merge only supplied fields. Practical row, canonical receipt and team activity summary commit in the same conditional partition transaction. Reused IDs with different content, stale revisions and revoked claims conflict. Any accepted nonempty response, including zero, records submitted activity permanently for guarded team deletion; clearing it later does not erase that history. Practical writes never change theory score or ranking timestamps. There is no automatic practical marking, final-submit action or answer lock; the competitor UI debounces valid edits for 500ms, flushes on blur/navigation and preserves errors or unsaved input instead of reporting false success.

## Recovery and leaderboard

`recovery` verifies current teacher code and expected epoch, issuing a short-lived single-use grant without changing role. Explicit Resume obtains fullscreen, then `resume` consumes the grant. Breach is locally synchronous and reported with epoch/request ID; stale epochs cannot undo a newer recovery. Fresh session?restore=1 revokes a competitor role session and expires its cookie, returning to access code and team selection without releasing claims or removing results. Teacher sessions are also revoked on fresh initialization. Ongoing recovery uses session?interrupt=1 to reconcile a lock without logging out. There is no periodic session poll or protected-operation preflight; each endpoint authenticates and fences its own action, and known schedule/session deadlines gate locally.

Teacher-only leaderboard uses the current unfinished event (active first, otherwise latest draft), no year selector, and returns authoritative top three nonzero scores: descending score, ascending last successful scoring time, then stable team ID. Read all pages. Poll immediately and every three seconds only while its screen/tab are visible, without overlap; preserve stale results with a stale indicator on failure.

## Pilot session lifecycle
Fresh page initialization clears both teacher and competitor authentication through session?restore=1 before login. The access forms render immediately. Login issues a session cookie (no persistent Max-Age); server expiry still applies. Each new teacher login has an isolated preview partition. Ordinary teacher previews start at revision zero without hydration; L6P3/U5P5 request their selected authorized state/data through question. Code management remains available only through the protected API.

## Draft testing
Competitor login uses the active event, otherwise the latest draft. Legacy multiple-draft stores use the latest until staff complete surplus events; there is no competitor chooser. GET availability is public and returns only {competitorAvailable: boolean}, true when a draft or active event exists. Draft gameplay uses the same persistent sessions, exclusive real-team claims, marking, cooldowns, outcome-only theory records, practical autosave and leaderboard as active gameplay. Both configured challenge starts and ends and overall expiry remain authoritative. Schedules are never replaced with synthetic windows. U5 has no practical. Empty rosters stay empty. Draft revision edits and worker recycling preserve sessions/results; activation retains start gating. Refresh revokes the session but retains the claim/results until teacher reselection. Submitted draft teams retain deletion protection even without prior activation, while unsubmitted teams retain guarded permanent deletion. Old practice-prefixed tokens fail with 401; authenticated POST practice-start returns 410 without replacing the cookie. No isolated practice service remains.


POST event-draft: teacher-only, {eventId, expectedRevision, confirm:true}; active events only. Returns updated session/settings. Preserves team records and results, increments event/config revisions, and records hasBeenActive. Reactivation retains scores and claims; completed events cannot return to draft.

POST event-year-change: teacher-only {eventId, expectedRevision, requestId, year, confirm:true, optional name/schedule fields}. Requires a different valid year and a draft/active event. Resets gameplay via a new event ID/data namespace, preserves team IDs, school metadata, allocation history and unlinked names, returns createdEventId and session/settings, and rejects old sessions. Repeating the same request is idempotent; changed payload conflicts. During staging, the event retains its validated `rosterResetInput` for explicit resume after failure/reload and blocks further event/roster edits. Retired storage remains outside the live event catalogue.

## Public readiness pilot

`GET pilot` returns `{status,revision,eventId,schools,rankings,snapshotAt}`. Status is `off|open`; legacy idle/closed states read as off. Schools are distinct linked schools with nonremoved teams in the current unfinished event. Public rankings contain at most three `{schoolId,name,rank}` entries, never scores or attempt IDs; they are empty while off. All responses are no-store.

`POST pilot-enter` takes `{schoolId,credential,requestId}`. The credential is 32 random bytes encoded as 64 hexadecimal characters. While on, it validates current school eligibility and creates or resumes one credential-owned attempt, returning `{id,schoolId,confirmedAt,best}`. First entry time is server-owned and immutable; retries and concurrent entry share the same attempt. Missing legacy times stay null. No accepted score is represented as `best:null`. No raw credential is stored.

`POST pilot-submit` takes `{schoolId,credential,requestId,graph}` for an entered attempt. The graph is JSON bounded to 120 KB inside a pilot-only 128 KB HTTP body ceiling (competition retains 64 KB). Response adds `{accepted,score}` to the attempt view. Rejected chemistry has `score:null` and preserves the best. Every component must be valid neutral C5H8; duplicate connectivities count once. No graph is retained. Frozen retries replay receipts; different payloads under the same request ID conflict. Off and ineligible schools reject submissions including retries.

`GET pilot-report` requires a teacher session and returns status/revision, current event/schools, and `readiness:[{id,schoolId,name,confirmedAt,best}]`. Each attempt is a separate row, sorted newest confirmation first; legacy missing times and absent scores are null. `POST pilot-mode` requires `{status:'open'|'off',expectedRevision,requestId}` and a teacher session. On/off is reversible without clearing data. Legacy `closed` requests map to off. Request-bound retries are idempotent, and conditional mode writes fence entry/submission atomically.

Pilot entry/submission retain same-origin/JSON/body checks and per-IP (180/minute) and per-credential (20/minute) limits. These are traffic limits, not school quotas. Browser-held pilot ownership grants no competition or teacher authority. See [pilot guide](readiness-pilot.md).

## Protected presentation delivery

The shared contract is `src/contracts/presentation.ts`. POST `question-content` takes `{questionId,eventId?}`; POST `practical-content` takes `{contentId?:year,eventId?}`. The versioned response is `{kind,id,schemaVersion:1,version,serverNow,presentation,assets:[{id,mimeType,bytes}]}`. Scientific titles, field labels/units/accessible names, prose and typed diagrams are presentation data. The public definition retains neutral routing metadata and generic edit validators. Scientific field/part/sample IDs and question-specific editor/default/validation configuration are protected too. `presentedDefinition` uses the authorized shape and IDs with the matching positional generic validators; CloudQuestion edits through this effective definition. Private marker IDs, request fingerprints and canonical receipts remain unchanged.

POST `content-asset` takes `{kind,questionId|contentId,version,assetId,eventId?}` and returns real SVG/PNG/JPEG/WebP bytes. It resolves only a fixed asset in the exact versioned record, never a requested filesystem path. Content and assets authenticate the same role/event/year/claim/security binding and start-inclusive/end-exclusive window in draft and active events, with authenticated teacher previews outside times. All responses are no-store/nosniff; SVGs are audited as trusted image geometry. Reads never allocate attempts or start timers. POST `content-catalogue` is teacher-only and returns presentation titles, without payloads/assets.

ContentStore pins successful versions in router-lifetime page memory, deduplicates in-flight loads and requires both result/state and content readiness before mounting. Logout, expiry, security lock, event/identity replacement or window closure abort loads and revoke blobs. Generation and current-window fences reject late responses even if abort is ignored; recovery reauthorizes. Failures remain retryable. No persistent/offline cache is used. All 35 theory and three practical records are explicitly registered; unsupported IDs remain unavailable. Selected timed/GC scientific data and obsolete selected-read flights are cleared and generation-fenced on theory closure or context/authority replacement without erasing learner working. Recovery/context return starts a fresh authorized read immediately; an old finalizer cannot clear its replacement, and current read failures expose Retry. Bulk feedback uses generic whole-question metadata even for legacy scientific part keys. See [the renderer contract](../.scratch/protected-question-content/renderer-seam.md). Local validation does not establish live Azure acceptance.

## School colour settings

Teacher POST `school-colours` accepts `{schoolId, colours, expectedRevision, requestId}` and returns `{school}`. `colours` contains exactly one or two `#RRGGBB` strings; accepted values are normalized to uppercase. Invalid colours return 400, missing/unauthorized sessions are rejected, and stale revisions or reuse of an ID with a different payload return 409. The school revision and directory revision advance atomically with a retry receipt in the system partition. This global presentation setting is editable independently of event completion; it changes no team claims, scores or allocations.

School records returned by `schools`, create/rename/colour responses, and pilot school listings include `colours`. Linked public teams include `schoolColours`; legacy unlinked teams omit it and use the frontend purple fallback. Absent stored palettes resolve on read from the approved preview defaults, with no migration writes. Pilot rankings retain their existing allowlist. Colours never grant selection or claim authority.

Teacher POST `school-delete` accepts `{schoolId,expectedRevision,requestId,confirm:true}`. It rejects the host, stale revisions, unfinished nonremoved teams and pending allocation plans. A system-partition transaction fences settings and directory changes and records an idempotent deletion receipt. The directory retains `deleted:true` and the reserved name for historical projections; teacher school lists include this flag, while selection and new allocations exclude deleted schools. No team, result or pilot history is deleted by this action.

Teacher POST `team-release` accepts `{eventId,teamId,confirm:true,requestId,expectedClaimGeneration}`. The request receipt and release commit atomically in the team partition. Exact retries return the current roster without releasing a newer claim; changed receipt input or stale claim generations return 409. Existing callers without requestId retain the legacy single-operation interface. Completed events and pending year resets reject new releases. Settings uses receipted releases for both single and bulk actions.

Teacher POST `teams-batch` accepts `{eventId,requestId,action,confirm:true,items}` with 1-100 distinct team IDs. Actions are `team-remove`, `team-restore`, `team-release` and legacy `team-delete`; item fields match the individual operation except eventId/requestId/confirmation, supplied by the envelope. Teacher POST `schools-import` accepts `{eventId,requestId,rows}` with 1-100 `{name,targetCount,colours,schoolId?,expectedRevision?,restore?}` rows. The full normalized import is validated before writes; existing schools require ID/revision from preview.

Both return `{requestId,total,completed,complete,results:[{index,ok,status?,error?}]}`. Jobs bind a canonical payload (maximum 48 KB) to the request ID and store per-item checkpoints. Exact retries skip completed items; changed payloads return 409. Teams/import rows run with at most three concurrent workers; restores serialize allocation reservations. Child operations reauthorize. Partial failures return explicit per-item errors; there is no cross-partition storage transaction. The browser refreshes once after the batch.

`school-create` with a normalized name matching a deleted school restores that same ID and current name/colours, increments its revision and atomically writes a request receipt. An active match still rejects duplicate creation. Exact retries do not restore again after a later deletion. Excel import previews this as Restore and then uses the existing colour/team setup endpoints. Historical team number reservations remain in force.


## Event team removal and restoration

Teacher POST `team-remove` and `team-restore` accept `{eventId,teamId,requestId,expectedEntryRevision,confirm:true}`. Team projections include `entryRevision` (existing rows start at zero). Removal increments it, retains withdrawal state, clears ownership/recovery and advances claim/security generations atomically with its receipt. Restoration increments it again; saved results stay in the same team partition. Linked restoration uses a request-bound school allocation plan to protect the 50-team limit and block concurrent school deletion. Deleted schools must be restored first. New events generate fresh team IDs linked to shared schools.

Teacher GET `removed-teams?eventId=...` returns `{teams}` for restorable withdrawals, including retained scores and entry revisions. Competitors cannot access this list. Removed teams are excluded from claims and leaderboards. Legacy destructive tombstones are excluded from restoration. New changes reject ended events, pending year resets and stale entry revisions. Exact retries do not undo subsequent lifecycle changes. The legacy `team-delete` contract remains unchanged.
