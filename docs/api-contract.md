# Application API contract

This contract describes the current implementation boundary. Server state and marking are authoritative. Browser presentation files contain no answer keys.

## HTTP and sessions

All endpoints use `/api/olympiad/{action}`. GET: `session`, `events`, `teams`, `leaderboard`, `diagnostics`. POST: `login`, `logout`, `event-create`, `event-update`, `event-activate`, `event-end`, `codes-update`, `team-add`, `team-release`, `team-delete`, `claim`, `start`, `breach`, `recovery`, `resume`, `hydrate`, `question`, `draft`, `submit`, `action`, `practical`, `practical-save`.

Opaque HttpOnly role cookie; server derives role/team/event/year. Teachers select an event with `eventId` on question/preview requests; competitors cannot override their bound event. Teacher sessions last eight hours. Codes initially 1234 competitor and 5678 teacher, hashed server-side; changes preserve issued sessions. Login returns a session snapshot. Logout never releases a claim.

Teacher catalogue previews use `eventId: catalogue-L5|catalogue-U5|catalogue-L6|catalogue-U6`. These validated year contexts do not create/edit events, bypass event timing and remain isolated and unscored. Competitors cannot use them to override their bound event or year.

Session snapshot: `{ role, expiresAt, serverNow, configRevision, activeEvent, events?, team, competition: {status, epoch}, score, attempts }`. `role` is `competitor` or `teacher`; absent authentication is 401. `activeEvent` is null or `{id,name,year,endsAt,status,revision}`. Team is null or `{id,name,eventId,year,claimGeneration}`. Competition uses NOT_STARTED/ACTIVE/LOCKED. Teacher previews have no team or competition score writes.

Events are draft/active/ended (displayed as Draft/Active/Complete), one unfinished event maximum (draft and active combined); creation is guarded by the conditional settings write. Drafts as well as active events may be completed with confirmation. Active year is immutable; ended events never restart. Schedules use UTC epoch milliseconds: `theoryStartsAt`, `theoryEndsAt`, `practicalStartsAt`, `practicalEndsAt`. New events require the theory pair; practical is an optional complete pair. Each start precedes its end; overlap between phases is permitted. `endsAt` is a derived compatibility output equal to the latest configured end. London wall-time forms reject nonexistent or ambiguous DST values. Legacy reads normalize theory start to null/unbounded, theory end to old endsAt and practical to null without rewriting stored events.

Ending/switching requires explicit teacher confirmation. Event edits/transitions carry `expectedRevision`; code changes carry `expectedConfigRevision`. Stale edits conflict rather than overwrite newer settings. `event-create` returns `createdEventId` so the client selects its own created event even during concurrent staff changes. Current event settings and server acceptance time define an in-flight operation snapshot; accepted work may finish against its original event. No cross-partition global transaction claim.

## Hydration and request policy

GO/start returns `hydration: {eventId,year,serverNow,eventEndsAt,score,questions}` with every registered question in the active year, including blank answer state, confirmed outcomes, revision and authorized public custom data. Teacher POST `hydrate` accepts `{eventId?}` and returns the same shape once per event/catalogue context. Reads use one question-partition listing and create no question/tick receipts. Public state may project elapsed timed/GC deadlines; completed state remains frozen. Private marking state and future timed prompts are never serialized.

Ordinary opening, editing and internal navigation use the in-memory cache and make no requests. CHECK sends one direct `submit`; retries retain its frozen ID/payload. Timed start/name checks/deadline and GC Run/completion retain necessary server actions. Practical autosave remains separate. No operation adds a session preflight, and there is no recurring session poll.

## Questions

`question` takes `{questionId,eventId?}` and returns `{attempt, revision, score, serverNow, eventEndsAt, data?}`; its compatibility `eventEndsAt` is the theory end. Competitor reads/submits/actions require the theory window. Claims/fullscreen entry/recovery use overall event availability, so competitors may enter before theory and wait in a countdown; closing theory hides content without creating a breach or resetting state. Teacher previews bypass theory timing. Practical uses a separate window and persistence contract below. Attempts retain the existing answers/feedback/retryAt/solvedAt/interaction presentation shape. Feedback is whole-question only. Additional public datasets (for example GC traces) use `data`; future timed answers never appear there.

`draft` is retired and returns 410 after access checks. The current frontend never calls it. Theory working stays only in mounted page memory: answers/drawings (including successful submissions), undo, group selections, GC formulation and reports. `submit` takes `{questionId,eventId?,requestId,answers}`; the marker evaluates that transient payload and persists only outcome/cooldown/completion metadata. Raw working is absent from new question rows and receipt snapshots for both competitors and teacher previews. Existing historical content is filtered on question/session/hydration reads and receipt replay, without a cleanup/migration or changing stored completed rows.

`action` takes `{questionId,eventId?,requestId,action}`. Only L6P3 `start`/`tick` and U5P5 `gc-run`/`tick` remain server operations. Retired grouping/GC presentation actions return 410. GC Run requires captured `{sample,concentration}`; the server chooses ID and a 4000ms deadline. Only the current run capture and next ID remain in the question record. A completion response/receipt carries `gcCompletedRunId`, not a report/measurement snapshot. The page builds its local report from its captured active run; fresh hydration has no report history. Run receipt snapshots keep ID/timing without the captured sample/concentration; the matching frozen request supplies those on retry. L6P3 retains the active sequence as private CSV row IDs plus prompt/progress/deadline, never the typed wrong name; inactive sequences are discarded on the next authorized write.

Responses retain the existing attempt shape but `answers` is empty. The page merges server outcome/timing into local working, clearing timed input when its prompt advances. Fresh entry starts with blank working; completed restored questions display their result/stamp without restoring their old answer. Request IDs bind operation/question/canonical payload through compact fingerprints and canonical outcome receipts. Same ID with different content is 409. Keep those receipts to prevent duplicate awards/restarted cooldowns; never recompute a replayed outcome from later state. Payload/HTTP size limits and ownership/security fences remain. Client clocks, score, correctness and year never authorize a mutation. Practical records and autosave are unchanged.

Backend marker module `api/src/questions.mjs` exports `questionInfo(id)` and `reduceQuestion(id, previous, action, now)`. Info is `{id,year,points,cooldownMs}`. Previous is `{state,privateState}`. Result is `{state,privateState,award}`; `award` is true only for the first unsolved-to-solved transition. Actions include `{type:'submit',answers}` and existing custom interaction actions, with all `now` fields ignored in favour of server time. Answer validation is separate from marking; retired draft requests cannot persist working. Custom module `api/src/custom-questions.mjs` exports `customInfo(id)` and `reduceCustomQuestion(id,previous,action,now)` (null for unsupported IDs). Private state is stored beside the public question state but never returned. Standard submissions do not return per-part feedback.

Team summary, question state and idempotency receipt share a per-team partition. Mutations conditionally fence the team claim/security generation and question revision. Release revokes ownership while retaining results and deadlines. Preview state is isolated from team partitions and never updates ranking.

Once solvedAt is confirmed, question state, private state and revision are immutable for subsequent accepted actions/ticks/submissions. Canonical receipts still bind new request IDs and reject reuse with different content; scores and ranking time cannot change again. The frontend freezes all question interactions without hiding readable scientific content or disabling header navigation.

`team-delete` is teacher-only and takes `{eventId,teamId,teamName,requestId,confirm:true}`. Completed events reject new deletions. Draft teams and active teams without submitted activity are permanently deleted; active submitted teams become retained excluded tombstones with reserved names. Activity includes zero-score wrong attempts and timed/server interactions, recorded atomically with submissions; older records are inspected compatibly. Both branches first revoke ownership/security generations and exclude the team from selection and ranking. Bootstrap/import/auth repair, team creation and deletion share one per-team lifecycle fence in their conditional transactions; an absent fence is guarded by transactional creation. Permanent cleanup retains that fence/admin receipts and uses conditional transaction chunks, preventing migration resurrection, stale generation reuse and stale cleanup deleting a recreated team. Reusing the same request is safe; the response includes `outcome: deleted|removed` and current teams. Development validation uses isolated memory data.

GC Enter, Load, dilution and report controls are local. Run sends one action with the captured sample/concentration; the server validates 0-100 in half-percent steps, keeps Mystery undiluted and starts the authoritative run. One completion action reconciles its deadline. Run IDs, deadlines, completed result snapshots and marking remain server-owned.

U5P7 retains the `drawings` field for both legacy carbon-only slot data and the shared editor's single molecule state. Local bounded undo history is stripped before transport/persistence. Legacy reads preserve atom IDs/connectivity through unique remapping, do not silently overwrite saved state, and retain oversized drafts intact in a read-only fallback. New submissions validate three distinct components against the unchanged private graphs after valid explicit/implicit hydrogen normalization. Question-specific editor bounds do not relax P3's existing defaults.

## Practical responses

`practical` takes `{eventId?}` and returns `{year,revision,responses,finalField,serverNow,eventEndsAt,readOnly,updatedAt}`. Each response is null or `{text,value}`: the exact entered numeric text and its finite parsed number. `practical-save` takes `{eventId?,requestId,expectedRevision,changes}`, where changes maps original response IDs to numeric strings or explicit null clears. Only the event year's fields are accepted: L5 and U6 use `numPracticalResponse1..4`; L6 uses only `numPracticalResponse3..4`. The final field is response4; a nonempty intermediate field does not constitute a final answer, and zero is not blank.

Competitor reads and writes require authenticated, ACTIVE Competition Mode with current ownership/security generations. The independent practical window authorizes writes; after its end, reads expose acknowledged responses read-only while the overall event remains available. Teacher practical screens use local-only inputs outside timing, with no save requests, save-status messages or navigation flush. Competitor saves and server authorization remain unchanged. Teacher `teams` results include practical working/final values for the selected event, including completed events.

Updates merge only supplied fields. Practical row, canonical receipt and team activity summary commit in the same conditional partition transaction. Reused IDs with different content, stale revisions and revoked claims conflict. Any accepted nonempty response, including zero, records submitted activity permanently for guarded team deletion; clearing it later does not erase that history. Practical writes never change theory score or ranking timestamps. There is no automatic practical marking, final-submit action or answer lock; the competitor UI debounces valid edits for 500ms, flushes on blur/navigation and preserves errors or unsaved input instead of reporting false success.

## Recovery and leaderboard

`recovery` verifies current teacher code and expected epoch, issuing a short-lived single-use grant without changing role. Explicit Resume obtains fullscreen, then `resume` consumes the grant. Breach is locally synchronous and reported with epoch/request ID; stale epochs cannot undo a newer recovery. Fresh session?restore=1 revokes a competitor role session and expires its cookie, returning to access code and team selection without releasing claims or removing results. Teacher sessions are also revoked on fresh initialization. Ongoing recovery uses session?interrupt=1 to reconcile a lock without logging out. There is no periodic session poll or protected-operation preflight; each endpoint authenticates and fences its own action, and known schedule/session deadlines gate locally.

Teacher-only leaderboard uses the active event, no year selector, and returns authoritative top three nonzero scores: descending score, ascending last successful scoring time, then stable team ID. Read all pages. Poll immediately and every three seconds only while its screen/tab are visible, without overlap; preserve stale results with a stale indicator on failure.

## Pilot session lifecycle
Fresh page initialization clears both teacher and competitor authentication through session?restore=1 before login. The access forms render immediately. Login issues a session cookie (no persistent Max-Age); server expiry still applies. Each new teacher login has an isolated preview partition. Ordinary teacher previews start at revision zero without hydration; U5P5 requests its required public data through question. Code management remains available only through the protected API.

## Draft testing
Competitor login opens the current draft as practice when no event is active. Legacy multiple-draft stores use the latest draft until staff complete surplus events; no competitor chooser is shown. GET availability is public and returns only {competitorAvailable: boolean}, true when a draft or active event exists. The access screen checks it on mount and window focus and disables competitor GO while unavailable or unverified. Authenticated POST practice-start accepts {eventId}, verifies competitor role and draft status, revokes the selection session and issues a replacement HttpOnly practice cookie. Practice snapshots only the selected draft?s public nonremoved team IDs/names into a separate in-memory repository on sign-in. Every copy starts unclaimed with zero results; real claims, answers, scores and security state are neither copied nor changed. Empty rosters retain the synthetic Practice team fallback. The selected draft?s year controls question routing and practical availability; synthetic challenge windows run until the practice session expires, independent of future/past saved schedules. U5 still has no practical. Practice uses real server marking, cooldowns, fullscreen and recovery. Only gameplay/session endpoints are allowed. No practice gameplay reaches durable competition storage. Worker loss/expiry returns 401; event activation or revision changes invalidate practice on its next request.

POST event-draft: teacher-only, {eventId, expectedRevision, confirm:true}; active events only. Returns updated session/settings. Preserves team records and results, increments event/config revisions, and records hasBeenActive. Reactivation retains scores and claims; completed events cannot return to draft.

POST event-year-change: teacher-only {eventId, expectedRevision, requestId, year, confirm:true, optional name/schedule fields}. Requires a different valid year and a draft/active event. Resets gameplay via a new event ID/data namespace, preserves team names, returns createdEventId and session/settings, and rejects old sessions. Repeating the same request is idempotent; changed payload conflicts. Retired storage remains outside the live event catalogue.

GET teams for competitors returns all nonremoved event teams with claimed:boolean, allowing disabled claimed tiles. Teacher-only scores, activity, practical data and security fields remain excluded. Claim remains server-authoritative; 409 requires refreshing the list, with no periodic team polling.

Incorrect login/recovery codes return 403 with `{error, code:"INVALID_CODE"}`. Clients show an invalid red CodePanels border/aria-invalid and no rejection paragraph; operational errors retain their messages.

## Read-only diagnostics

GET diagnostics requires a current teacher session (unauthenticated 401, competitor/practice 403) and returns Cache-Control: no-store. It performs no settings mutation, team listing or health-test write. The explicit projection includes snapshot/server runtime metadata, repository/storage-presence status, settings revision, access-code configured booleans, current active/latest-draft selection, legacy testing-event ID, and allowlisted event identity/status/revision/times/source hints.

Production reads only OLYMPIAD_STORAGE_CONNECTION_STRING, OLYMPIAD_EVENT_ID and OLYMPIAD_EVENT_END. The storage value is never returned. The ID is returned only when it passes the application's bounded ID validation; the end is returned only as a valid epoch instant, never invalid raw text. ID/end are legacy bootstrap configuration, not live overrides of persisted settings. Programmatic/local repositories report their known source and unknown storage presence honestly. Unknown config/settings/environment fields, initial code values, hashes, tokens, cookies, storage keys, connection strings, personal/team data and arbitrary environment dumps are excluded. UI tables display UTC ISO, Europe/London and epoch milliseconds without exposing a raw settings object.

Backend settings is independent of the editable event form: first expansion loads one snapshot, collapse/reopen retains it, manual Refresh/Retry reloads, and no polling or automatic form reset occurs. The Event status dropdown retains the same confirmation/revision-guarded commands; redundant lifecycle buttons and event-toolbar Preview practical are absent. The practical catalogue remains under Preview Questions.
